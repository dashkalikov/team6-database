# VC-74: игровые операции в транзакциях

## Реализованный объём

Модели wallets, rounds, wallet_operations и базовые coupons/coupon_redemptions. Один синхронный спин выполняется сервисом play_round в одной внешней транзакции. Базовый сервис redeem_coupon обеспечивает согласованный источник монет при начальном балансе 0. HTTP API, вход, интерфейс купонов, администраторский аудит и отдельный возврат после завершённого спина в эту задачу не входят.

При создании пользователя через User.objects.create_user одновременно создаётся кошелёк с балансом 0. Миграция создаёт пустые кошельки для ранее существовавших пользователей. Автоматического стартового начисления и ручного сервиса изменения баланса нет.

## Контракт спина

```python
from uuid import uuid4
from finance.services import play_round

# user_id берётся из проверенной авторизации серверного слоя.
# Ключ создаётся один раз на действие; повтор запроса использует тот же ключ.
request_key = uuid4()
round = play_round(
    user_id=user_id,
    game_id=game_id,
    request_key=request_key,
    bet_amount=10,
)
```

Клиент не передаёт grid, коэффициент или payout. Результат формируется на сервере через games.engine.spin по сохранённой версии правил. Стоп-позиции выбираются secrets.randbelow, видимые символы берутся из циклических лент. Вычисления используют Fraction. Совпавшие линии суммируются, итог округляется вниз один раз; ставка отдельно к выигрышу не прибавляется. Дробный остаток при распределении amount по линиям переносится вперёд в порядке paylines: сумма целых line.amount равна payout_amount. Число линий и их порядок фиксируются версией правил.

Порядок одной транзакции:

1. Проверка формата ключей, целочисленной положительной ставки и активного пользователя. Строка пользователя блокируется FOR UPDATE.
2. Поиск прежнего раунда по (user_id,request_key). При совпадении игры и ставки возвращается сохранённый результат без RNG и записей; при иных параметрах — RequestConflict. Смена правил и отключение игры не меняют прежний результат. Заблокированный пользователь не может вызвать сервис даже для повторного запроса.
3. Блокировка игры FOR SHARE, получение текущей версии, проверка активности и лимитов. Блокировка кошелька FOR UPDATE и проверка достаточности средств.
4. Расчёт результата и создание completed-раунда. Родительская строка создаётся перед операциями из-за FK.
5. Списание ставки, bet_debit с промежуточным balance_after; при ненулевой выплате — начисление и win_credit с окончательным balance_after.
6. Проверка отложенных ограничений и COMMIT всех изменений. Результат возвращается только после успешного COMMIT.

Ошибка в расчёте, вставке, изменении баланса или отложенном ограничении откатывает весь спин. При проигрыше сохраняются результат, payout_amount=0 и одна операция списания. pending/cancelled и refund_credit зарезервированы в проектной схеме, но запрещены ограничениями текущего синхронного пути. Ошибка спина не создаёт отменённый раунд или возврат: списание исчезает при ROLLBACK.

Сервис использует transaction.atomic(durable=True) и не допускает вызова внутри чужой транзакции. При подключении к HTTP его нельзя оборачивать в ATOMIC_REQUESTS или дополнительный atomic: это обеспечит, что ответ выдаётся после фактического COMMIT. Дополнительные внешние эффекты выполняются после фиксации, анимация — на клиенте.

Известные отменённые PostgreSQL-транзакции с SQLSTATE 40001/40P01 повторяются не более трёх раз. Другие ошибки не скрываются. Ошибка связи во время COMMIT не означает гарантированного отката: клиент повторяет исходный ключ, чтобы прочитать сохранённый результат или выполнить заново полностью отменённый запрос. Потерянный ответ не является основанием для нового ключа.

## Защита PostgreSQL

- UNIQUE(user_id,request_key), UNIQUE(round_id,type), положительные суммы, неотрицательный баланс, статус completed и объектный JSON результата.
- Составные FK проверяют владельца кошелька и принадлежность операции кошельку её раунда/активации.
- Триггеры запрещают UPDATE/DELETE финансового журнала, раундов и активаций. Идентификатор/владелец кошелька и код/создатель купона неизменяемы.
- При INSERT операции её balance_after проверяется против текущего кошелька и предыдущей суммы журнала под блокировкой кошелька.
- DEFERRABLE INITIALLY DEFERRED constraint triggers перед COMMIT проверяют баланс = сумме начислений минус списания, ровно одно списание ставки на раунд, соответствие суммы выигрыша и наличие ровно одного начисления на активацию купона. Транзакция с отсутствующей записью выигрыша отклоняется целиком.

Миграция 0002_integrity_guards обязательна: она создаёт составные FK и триггеры, которые не выражаются целиком стандартными полями Django. Обход этих ограничений владельцем схемы, TRUNCATE или отключением триггеров не является прикладным путём. При развёртывании роль приложения отделяется от роли миграций; ей не выдаются TRUNCATE/DDL и права UPDATE/DELETE финансовой истории. ORM-сервисам требуются SELECT и ограниченные INSERT/UPDATE кошелька; прежняя идея только EXECUTE на SQL-процедуры не используется в этой реализации.

Проверка суммы журнала сейчас читает историю кошелька. Это осознанная стоимость контроля для учебного MVP; перед масштабированием требуется измерить запросы и выбрать способ ускорения с сохранением гарантий.

## Купоны и регистрация

redeem_coupon — внутренний сервис с одним внешним atomic. Общий бессрочный купон может быть активирован каждым пользователем один раз. Под блокировками сохраняются активация с фактическим номиналом, баланс и coupon_credit. Повтор возвращает прежнюю активацию даже после отключения купона или изменения его номинала. Управление купонами и полномочия администратора должен реализовать отдельный административный слой; прямой доступ конечных пользователей к ORM отсутствует.

create_user создаёт пользователя и нулевой кошелёк в одной транзакции; ошибка создания кошелька откатывает пользователя. Запись через bulk_create/сырой INSERT users не заменяет этот контракт. Пользователи, существующие до миграции finance, получают нулевые кошельки при миграции.

## Применение

После настройки переменных PGHOST, PGPORT, PGDATABASE, PGUSER, PGPASSWORD из корня проекта:

```powershell
.\.venv\Scripts\python.exe backend/manage.py migrate --plan
.\.venv\Scripts\python.exe backend/manage.py migrate
.\.venv\Scripts\python.exe backend/manage.py test accounts games finance
```

Основная локальная база не изменяется выполнением тестов: Django создаёт и удаляет отдельную тестовую БД. Пользователь тестового подключения должен иметь право её создания. Рабочие пароли и дампы в Git не сохраняются.

## Проверка VC-74

Проверки на PostgreSQL охватывают выигрыш и проигрыш, откат после каждой финансовой записи и вставки раунда, исключение расчёта, переполнение, отказ от неполного журнала при COMMIT, повторные ключи и конфликт параметров, две параллельные попытки с одним ключом, недостаточный остаток при разных ключах, невидимость промежуточных данных другому соединению, неизменяемость истории, атомарность регистрации и активации купона. Тесты accounts/games выполняются вместе с finance для проверки совместимости.

Результат проверки: 32 теста accounts/games/finance прошли совместно; отдельно прошёл тест обновления базы с существующими пользователями, включая обратное применение финансовых миграций и повторный переход вперёд. Всего проверено 33 теста. Системная проверка Django и проверка отсутствующих миграций проходят.
