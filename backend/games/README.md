# VC-67: каталог игр и версии правил

Реализованы модели Game и GameRuleVersion, миграции, сервисы управления каталогом, валидация правил и демонстрационный слот 3×3. В рамках VC-67 реализована структура правил. В VC-74 добавлен games.engine.spin и атомарный финансовый сервис; описание приведено в ../finance/README.md.

## Игры

Game хранится в games. Код уникален, нормализуется через strip/lower и содержит 1–64 символа a–z, 0–9, _. Название непустое после strip, до 120 символов. Описание и тема необязательны. Новая игра неактивна и может не иметь текущей версии. Активная игра обязана иметь current_rule_version.

Предметные UUID создаются uuid.uuid4 в ORM. created_at и updated_at задаются ORM, updated_at обновляется при save, в том числе с update_fields. QuerySet.update не выполняет нормализацию и не обновляет updated_at; прикладные изменения выполняются через save и сервисы.

Составной FK games(id,current_rule_version_id) → game_rule_versions(game_id,id) добавлен SQL-миграцией 0002_history_guards. Он запрещает выбор версии другой игры, в том числе через прямой UPDATE. Поле ORM имеет db_constraint=False, поскольку фактическую ссылочную целостность обеспечивает составное ограничение. Эту SQL-миграцию необходимо сохранять вместе с автоматически созданной миграцией.

## Версии

Версии неизменяемы с момента создания. Изменение настроек создаёт новую строку. Номер версии положителен и уникален в пределах игры. min_bet>0, max_bet>=min_bet. Пары game/version и game/id защищены UNIQUE.

Триггер PostgreSQL запрещает UPDATE/DELETE правил даже при обходе save. Роль приложения при развёртывании не должна иметь права TRUNCATE, изменения схемы или отключения триггеров. На этапе разработки тесты работают под владельцем отдельной тестовой базы; разделение ролей развёртывания не входит в эту задачу.

add_rule_version блокирует строку игры до выбора следующего номера и сохранения версии. Два параллельных вызова получают последовательные уникальные номера. select_rule_version проверяет принадлежность и меняет только указатель. Деактивация исключает игру из get_catalog, сохраняя все версии. Удаление игры с версиями блокируется PROTECT.

## Формат правил

Точный пример: [examples/slot_3x3.json](examples/slot_3x3.json). Валидатор отклоняет неизвестные поля и неподдерживаемые значения:

| Поле | Контракт |
|---|---|
| format_version | Целое 1 |
| reel_count / row_count | Целые 3 / 3 |
| symbols | 2–64 уникальных кода, 1–32 символа A–Z, 0–9, _, первый знак — буква |
| reels | Три ленты по 3–256 позиций, только известные символы; повторение символа задаёт вес |
| paylines | 1–27 фиксированных линий, уникальные id и пути |
| paylines[].rows | Три индекса 0..2: по одной строке для каждого барабана слева направо |
| paytable | 1–1024 уникальных точных комбинации из трёх символов |
| multiplier | Положительные целые numerator/denominator, каждый до 1000000; bool/float запрещены |
| payout | Фиксированный контракт расчёта, описанный ниже |

Видимое поле результата задаётся grid[row][reel], строки сверху вниз. Ленты циклические; три видимых символа соответствуют трём последовательным позициям. Выбор стоп-позиций реализован в games.engine.spin через secrets.randbelow (VC-74).

Общая ставка относится ко всему спину и списывается один раз. Все сохранённые линии включены; выбора числа линий клиентом нет. Каждая линия проверяется на точное совпадение трёх символов. Wild/scatter и бесплатные вращения в format_version=1 не входят.

Коэффициент задаёт начисление по линии с учётом ставки. Трактовка для будущего расчёта: payout = floor(bet_amount × сумма точных дробных коэффициентов совпавших линий). Промежуточные значения не округляются, дополнительный возврат ставки не прибавляется. Например, ставка 10 и одна линия с коэффициентом 2 означают начисление 20; ставка 5 и две линии с коэффициентом 1/3 означают начисление floor(10/3)=3. Расчёт по этому контракту реализован в games.engine.spin (VC-74).

В настройках: bet_basis=spin_total, includes_stake=true, rounding=floor, aggregation=sum_then_floor, line_match=exact_three. Консервативная проверка max_bet × число линий × наибольший коэффициент исключает выход возможной выплаты за signed bigint. Вероятности и демонстрационные коэффициенты не являются оценкой RTP или утверждённым балансом игры.

Глубокая валидация JSON выполняется моделью и сервисами. В БД проверяются объектный тип config, первичные/внешние ключи, диапазоны ставок и неизменяемость; прямой bulk_create/SQL INSERT не проверяет весь JSON-контракт и не используется как прикладной путь записи.

## Применение и пример

Из корня проекта, после настройки PGHOST/PGPORT/PGDATABASE/PGUSER/PGPASSWORD:

```powershell
.\.venv\Scripts\python.exe backend/manage.py migrate
.\.venv\Scripts\python.exe backend/manage.py seed_demo_game
.\.venv\Scripts\python.exe backend/manage.py test accounts games
```

seed_demo_game создаёт неактивную demo_slot с пятью линиями, тремя символами и ставками 1–100. Повторный запуск не перезаписывает существующую игру. Коэффициенты и ленты служат демонстрацией формата. Игра включается отдельно после принятия настроек:

```python
from games.models import Game
from games.services import get_catalog, set_game_active

game = Game.objects.get(code="demo_slot")
set_game_active(game.id, True)
catalog = get_catalog()
```

Сервисы предназначены для доверенного серверного кода. Авторизацию вызывающего администратора должен проверять будущий API/административный слой.

## Проверка

На PostgreSQL выполнены миграции и 9 проверок games: поля и дубликаты, выбор версии, каталог и деактивация, сохранение прежних правил, запрет изменения/удаления, межигровая ссылка, неверные лимиты/JSON, повтор загрузки примера, два параллельных соединения. Вместе с 7 проверками accounts — 16 успешных тестов. Миграции games не создают rounds/wallets; они добавлены миграциями finance в VC-74.
