# Ограничения, транзакции и проектная проверка

Документ определяет требования к целостности данных для Django/PostgreSQL. Предметные таблицы описаны в data-dictionary.md, служебные — в django-schema.md; диаграмма schema.mmd показывает логические кратности. Обязательное создание кошелька, операции активации и списания раунда обеспечивается транзакционными процедурами. Документ не является результатом проверки работающей реализации.

## Кратности и удаление

- Пользователь → кошелёк: ровно один после успешной регистрации; технически FK + UNIQUE допускают отсутствие до создания кошелька.
- Пользователь → раунды: 0..N; каждый раунд принадлежит одному пользователю и одному его кошельку.
- Игра → версии: 0..N при подготовке; активная игра имеет текущую версию. Версия относится ровно к одной игре.
- Версия → раунды: 0..N; каждый раунд использует ровно одну неизменяемую версию.
- Купон → активации: 0..N; на пользователя не более одной активации данного купона.
- Кошелёк → операции: 0..N; каждая операция относится ровно к одному кошельку.
- Раунд → операции: одно списание, затем ноль или одна итоговая операция. Проигрыш завершён, но выплаты в журнале нет.
- Активация → операция: ровно одно начисление после COMMIT. Операция ссылается либо на активацию, либо на раунд.

Исторические FK предметного ядра защищены от каскадного удаления. Поведение штатных FK Django описано отдельно в django-schema.md. Для пользователя используется блокировка, для игры/купона — деактивация. Журнал и активации неизменяемы; завершённый или отменённый раунд и опубликованные правила неизменяемы. Исправление истории через UPDATE запрещено. Компенсирующие операции требуют отдельного контракта: произвольного admin_credit в MVP нет.

## Защита инвариантов

CHECK проверяет одну строку: положительные суммы, допустимые состояния, форму связей операции. UNIQUE защищает от дублей, составные FK — от связи с чужим кошельком/игрой. Соответствие суммы операции ставке/активации, обязательность операции, переходы статуса и равенство баланса сумме журнала требуют общей транзакции.

Финансовые операции реализованы ORM-сервисами finance.services с внешним transaction.atomic(durable=True). Роль приложения получает SELECT и необходимые INSERT/UPDATE кошелька, без UPDATE/DELETE финансовой истории, TRUNCATE и DDL. Роль миграций отделяется от runtime при развёртывании. Согласованность перед COMMIT дополнительно проверяют отложенные constraint triggers PostgreSQL; неизменяемость истории обеспечивают отдельные триггеры. Отдельные SQL-процедуры с SECURITY DEFINER в этой реализации не используются.

Аутентифицированный user_id поступает из доверенного серверного контекста, не из непроверенного тела запроса. Сервисы проверяют active пользователя. HTTP-авторизация и административные полномочия относятся к будущему API-слою.

## Общий протокол блокировок

Уровень изоляции: READ COMMITTED с явными блокировками строк и ограничениями уникальности. Все пути, включая администрирование, соблюдают порядок: пользователь → игра (если нужна) → купон (если нужен) → кошелёк → существующий раунд. Пользователь блокируется FOR UPDATE для согласования с блокировкой аккаунта; при нескольких пользователях — по id. Для игры при ставке применяется FOR SHARE, при смене версии — FOR UPDATE. Для купона/кошелька/раунда — FOR UPDATE. Действия одного пользователя сериализуются.

После ожидания блокировки условия перечитываются. Не выполнять сетевые вызовы под блокировками. Deadlock/serialization failure: откат и ограниченный повтор всей транзакции с тем же ключом. Потеря ответа после COMMIT: повтор возвращает сохранённый результат.

## Границы транзакций

### Регистрация

В одной транзакции создать users и wallets(balance=0), затем COMMIT. Конфликт логина/email откатывает обе записи. Начальный ноль не создаёт coupon_credit или registration_bonus. Отдельный ключ идемпотентности регистрации отсутствует: повтор с тем же логином отклоняется как дубликат.

### Купон

1. Заблокировать пользователя, купон, кошелёк; проверить принадлежность кошелька.
2. Найти существующую активацию (coupon_id,user_id): если есть, вернуть её и связанную операцию. Отключение купона или изменение номинала не отменяет сохранённую активацию.
3. Проверить active пользователя и is_active купона. Купон бессрочный; общий лимит в текущую схему не включён. Все пути активации и редактирования используют блокировку купона.
4. Вставить активацию с текущим amount; увеличить баланс; вставить coupon_credit с тем же amount и balance_after. COMMIT всех трёх изменений вместе. Проверить переполнение bigint: ошибка откатывает всё.

UNIQUE(coupon_id,user_id) и UNIQUE(redemption_id) — дополнительная защита. При конфликте не продолжать транзакцию после SQL-ошибки: откатить и прочитать результат новой транзакцией либо использовать корректный ON CONFLICT без повторного финансового эффекта.

Администратор редактирует купон под той же блокировкой, с проверкой роли. code/id неизменяемы после публикации. Сумма прошлых активаций не пересчитывается. Изменение записывается в прикладной аудит той же транзакцией. Политика полного аудита правок требует отдельного решения.

### Атомарный спин

Весь синхронный раунд выполняется в одной транзакции PostgreSQL. В Django граница задаётся одним внешним transaction.atomic(); вложенные savepoint не заменяют общий COMMIT.

1. Начать транзакцию и заблокировать пользователя. По (user_id,request_key) проверить существующий раунд. При совпадении игры и bet_amount вернуть сохранённый результат без RNG и финансовых записей; при различии — ошибка конфликта ключа. Проверка принадлежности и полномочий обязательна и для повторного чтения.
2. Для нового запроса заблокировать игру FOR SHARE, проверить её доступность и получить текущую неизменяемую версию правил. Заблокировать кошелёк FOR UPDATE, перечитать баланс, проверить владельца, active пользователя, допустимость ставки и достаточность монет.
3. Рассчитать результат на сервере по выбранной версии правил. RNG, если используется, вызывается внутри этой попытки; сетевые вызовы и ожидание анимации внутри транзакции запрещены.
4. Списать bet_amount из кошелька и записать bet_debit с промежуточным balance_after. Сохранить rounds с версией правил, полной grid 3×3, выигравшими линиями, payout_amount, status=completed и временем завершения. Порядок INSERT раунда и операций определяется FK; раунд может быть вставлен перед операциями в рамках той же транзакции.
5. При payout_amount>0 увеличить баланс и вставить win_credit с окончательным balance_after. При проигрыше payout_amount=0 и отдельной нулевой операции нет.
6. Проверить согласованность сумм и выполнить один COMMIT. Только после успешного COMMIT отправить клиенту результат для анимации.

Ошибка на любом шаге откатывает раунд, обе операции и изменение кошелька. Ошибочный запрос не сохраняется как cancelled и не создаёт refund_credit: при ROLLBACK списание исчезает вместе со всеми изменениями. Диагностические ошибки могут попадать в технические логи без секретов; это не финансовые операции.

В READ COMMITTED другие запросы не видят промежуточный остаток кошелька. После COMMIT они видят итоговый баланс; журнал содержит отдельные суммы списания и начисления. Эти строки относятся к одной атомарной операции.

UNIQUE(user_id,request_key), UNIQUE(round_id,type) и блокировки защищают повторные/параллельные запросы. После потери ответа клиент повторяет тот же request_key. Если COMMIT состоялся, сервер возвращает прежний результат. Если транзакция была полностью отменена, повтор может рассчитать новый результат: незавершённый результат клиенту не выдаётся. При ошибке соединения во время COMMIT исход нельзя считать известным без повторного чтения по ключу.

Блокировка пользователя сериализует его запросы. Две ставки с разными ключами проверяются последовательно на фактическом балансе. Выигрыш первой ставки может увеличить доступный баланс для следующей.

### Выплата и резервные состояния

Ставка общая на спин, линии фиксированы, коэффициент задаёт начисление с учётом ставки. Контракт format_version=1: сумма точных дробных выигрышей округляется вниз один раз; дополнительный возврат ставки не прибавляется. Выплата вычисляется сервером, а не берётся из клиентского запроса.

В схеме сохраняются pending/cancelled, cancellation_reason и refund_credit как резерв ранее описанного сценария возврата. Синхронная процедура play_round фиксирует только completed. Она не выполняет промежуточный COMMIT со статусом pending и не требует отдельного обработчика завершения или таймаута pending.

Отдельный возврат после уже зафиксированного спина не является откатом транзакции. Его полномочия, переходы состояний, связь с исходным выигрышем и ограничения журнала требуют самостоятельного контракта до реализации; текущая процедура его не предоставляет. История completed не переписывается ради исправления ошибки.

## Проверочные сценарии (расчёт вручную)

| Сценарий | Ожидаемый результат | Защита |
|---|---|---|
| Регистрация → купон 100 → спин со ставкой 10 и выплатой 20 → история | Зафиксированные балансы 0 → 100 → 110; журнал +100,-10,+20 | Купон и спин — по одной финансовой транзакции; списание и выплата спина фиксируются вместе |
| Ставка 10 проиграна | payout=0, баланс 90, только списание | completed/result, отсутствие нулевой операции |
| Ошибка после списания до фиксации результата | Баланс 100, ни раунда, ни списания/выигрыша в журнале | ROLLBACK всего спина; refund_credit не создаётся |
| Два одновременных ввода купона одним пользователем | Одна активация и +100 всего | Блокировки, UNIQUE пары и redemption_id |
| Один код у двух пользователей | По одной активации каждому | UNIQUE пары, а не coupon_id |
| Администратор меняет amount во время активации | Начисляется целиком старый или новый номинал | Общая блокировка купона, снимок amount |
| Баланс 15, два проигрышных спина по 10 с разными ключами | Один завершён, второй отклонён, остаток 5 | Блокировка и перечитывание баланса |
| Повтор одной ставки после потери ответа | Тот же раунд, одно списание | request_key + сравнение параметров |
| Один ключ, другая ставка/игра | Ошибка конфликта | Проверка параметров существующего раунда |
| Два обработчика получают один request_key | Один раунд и по одной операции списания/ненулевого выигрыша | Блокировки и UNIQUE |
| Соединение потеряно после COMMIT | Повтор возвращает сохранённый результат без новых операций | Поиск по request_key до RNG и записи |
| Изменена текущая версия игры | Старый раунд использует старую версию | Неизменяемый rule_version_id и config |
| Ошибка между журналом и изменением баланса | Никаких частичных изменений | ROLLBACK общей транзакции |
| Блокировка пользователя | История остаётся, новых ставок нет | status и RESTRICT |

Сверка в согласованном снимке: wallets.balance = SUM(credit amounts) - SUM(bet_debit amounts), исходный остаток 0. Дополнительно проверить ровно один bet_debit на раунд, ровно один coupon_credit на активацию и соответствие сумм; для синхронного completed с payout>0 ровно один выигрыш, при payout=0 ни одного. Дополнительно проверяется отсутствие зафиксированного pending, созданного процедурой play_round. Эта сверка диагностическая, не заменяет атомарную запись.

## Открытые параметры реализации

1. Отображение DB-default в миграциях и окончательная нормализация логина, email и кода.
2. Конкретные разрешения группы администраторов, срок сессий и механизм их отзыва.
3. Полный перечень аудируемых действий; купоны бессрочные, общий лимит в MVP отсутствует.
4. Окончательные ленты/комбинации и коэффициенты игры; отдельный контракт возврата после COMMIT при включении этой функции.

VC-74 реализует модели и миграции финансового ядра, ORM-сервисы, серверный расчёт и испытания ошибок/параллельных запросов на PostgreSQL. Подробности и границы проверки описаны в ../../backend/finance/README.md. Открытые параметры администрирования и отдельного возврата фиксируются до реализации этих функций.
